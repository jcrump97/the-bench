# QA Agent

`run-the-bench` verifies the fixed, hand-authored demo docket against a
committed script — useful for UI regressions, useless for catching problems
in what the *live* Gemini pipeline actually writes. This skill closes that
gap: it plays a real, freshly-generated BYOK case with Playwright, and at
every beat asks a second, independent Gemini call — playing a meticulous,
technically literate human QA tester — to judge the content for realism and
verbiage problems and any UI/UX issue visible on screen, and (at real
decision points) to choose what a player would actually click.

Built after a live-tested case had a party say "the jury is entitled to hear
it" in a game that is always a bench trial — a bug no automated check caught,
because `npm test` is fully mocked and the other live suites only check
response *shape*, never prose content.

## Cost and non-determinism — read this first

**Every run spends real, billed Gemini API quota twice over**: once for the
actual case-generation pipeline (the same multi-stage `GameService` calls
BYOK players trigger) and again for every beat's QA-judgment call (text +
screenshot). A full case is commonly 20–60 beats. This is not free and not
fast (multi-stage generation alone can take a minute or more; expect a
10–20 minute full run).

Both the generated case *and* the QA judgments are live LLM output, so
findings and even the exact path taken through the game will differ between
runs. This tool is a human-review aid, not a correctness gate — **never**
add it to `npm test`, `npm run lint`, `npm run build`, a git hook, or CI.
(Compare `npm run test:live`, which has the same live-API caveat.)

## Prerequisites

Same throwaway Playwright install as `run-the-bench` — skip this if you've
already run that skill in this environment:

```bash
npm i --prefix /tmp/bench-playwright playwright
npx --prefix /tmp/bench-playwright playwright install chromium-headless-shell
```

A repo-root `.env` with a real key:

```
GEMINI_API_KEY=AIza...
```

## Run

```bash
npm run dev &   # serves http://localhost:5173/the-bench/
node .claude/skills/qa-agent/qa-agent.mjs
```

Run from the repo root (the script reads `.env` relative to `process.cwd()`,
same as `src/lib/llm/__tests__/live/liveEnv.ts`).

Knobs (all optional):
- `BASE_URL` — default `http://localhost:5173/the-bench/`.
- `PLAYWRIGHT_PREFIX` — default `/tmp/bench-playwright`.
- `PW_EXECUTABLE_PATH` — point at a pre-installed browser instead of
  Playwright's bundled one.
- `QA_REPORT_DIR` — default `/tmp/bench-qa-report`. The Markdown report and a
  `screenshots/` subdirectory (one PNG per beat) land here.
- `QA_MAX_ITERATIONS` — default `150`. Safety cap so a stuck run doesn't spin
  forever.
- `QA_GENERATION_TIMEOUT_MS` — default `480000` (8 min). How long to wait for
  BYOK case generation before treating it as a hard failure. The six-plus
  sequential Gemini calls behind generation can each retry-with-feedback on a
  validation failure, plus one bounded repair round — a slow run can
  legitimately take several minutes.

## What it does

1. Opens the Welcome screen, submits the `.env` key through the real BYOK
   form, clicks Continue, and waits for the live pipeline to either land in
   the courtroom or fail into `ErrorScreen` ("Mistrial") — the latter is a
   hard FAIL, not retried.
2. At every beat, reads the newly-revealed transcript text (`main` innerText,
   diffed against what was already reviewed) and a screenshot, and enumerates
   the current `[data-action-bar]` controls:
   - **A single button** (a statement continue, or a forced transition like
     "Order Trial"/"Adjourn") → review-only judgment call, then click it.
     "Skip to Next Decision" is deliberately never the chosen button — a real
     first-time player reads everything.
   - **Two or more `data-choice` buttons** (plea ruling, motion ruling,
     verdict) → a review-and-decide call; Gemini picks the option a player in
     that spot would pick, with reasoning. An out-of-range/invalid choice
     falls back to the first option and is logged as a fallback, distinct
     from a real finding.
   - **Sentencing** (`input[type=number]` fields) → Gemini gets each line
     item's floor/ceiling (read straight off the rendered `min`/`max`
     attributes) plus the demeanor notes, and returns an amount per item;
     out-of-range amounts fall back to the floor.
3. Once "New Case" appears, does one last review call on the aftermath, then
   stops (does not click New Case, to keep the finished record intact for the
   report).
4. Writes `$QA_REPORT_DIR/report-<timestamp>.md` (findings table sorted by
   severity, the full action-by-action decision log with reasoning, and the
   complete transcript) and prints a `HIGH`/`MEDIUM`/`LOW` line per finding
   plus a final PASS/FAIL summary, in that order, to the console.

Exit code is non-zero if generation failed, the run got stuck past
`QA_MAX_ITERATIONS`, or any finding was `HIGH` severity. `MEDIUM`/`LOW`
findings are informational and don't fail the run.

## Gotchas

- Uses its own small, standalone Gemini client and `.env` loader — it can't
  `import` `src/lib/llm/*.ts` or `liveEnv.ts` from a plain `.mjs` script
  without a build step, so those are intentionally duplicated in miniature
  here rather than shared.
- The QA-judgment model is picked dynamically (same `ListModels` discovery
  idea as `src/lib/llm/modelSelection.ts`) but prefers the `flash` tier over
  `flash-lite` — judgment quality matters more than cost for this role. Case
  *generation* itself still goes through the real app's own cost-optimized
  `GameService` model selection, untouched by this script.
- If the dev server is on a non-default port (Vite picks 5174+ when 5173 is
  busy), set `BASE_URL` to match, same as `run-the-bench`.
